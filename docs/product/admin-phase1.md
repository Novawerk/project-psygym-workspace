# 后台第一期

**状态：范围定稿（2026-10-15），接口已和后端对齐，以 ADR 0009 和 `docs/admin-api.md` 为准。** 方案和已定的决定（D-A1–D-A10）见 [admin.md](./admin.md)。本文只写第一期做什么、页面长什么样、页面上的中文怎么写。本文第 7 节是和后端对齐后的约定。

设计稿：Design 画布第 ⑩ 行「后台」。

## 一句话

Novawerk 和聆镜的人用 Google 登录 `admin.psygym.novawerk.io`，看匿名的使用数据，在网页上改病例和督导标准、发布、回滚。服务端不存对话，这一条不变。

## 0. 第一期做什么、不做什么

| 做 | 不做（第二期） |
|----|----------------|
| Google 登录；`admins` 表；第一位管理员用后端命令开 | 邀请码管理（仍在环境变量里） |
| 数据看板：按天 / 按周的折线和表，按病例、语言筛选 | 账号管理（App 用户）和后台人员管理页面 |
| 病例和督导标准：列表、编辑、草稿、预览、试聊、发布、版本历史、回滚、发布记录 | GitHub 单向同步（要建 GitHub App，步骤见第 8 节） |
| 发布和回滚时发 Slack #project-psygym | 病例下架；督导标准的「试评」 |
| | 「待审 / 退回」流程（D-A9：可以自审，第一期直接发布） |

**和 admin.md 不一样的地方：**

- **角色从四种并成三种。** admin.md 里的「审核人」并进「编辑」：编辑能改、能发布、能回滚。D-A9 定了可以自己审自己，单独的审核人角色在第一期没有区别。
- **没有「待审」和「退回」。** 状态只有「草稿」和「已发布」。发布留痕、Slack 通知、一键回滚这三条补偿措施第一期都上。
- **GitHub 同步放到第二期。** 第一期上线后，数据库就是病例和督导标准的来源；开源仓库的 `content/` 由我们在每次发布后手动导出更新（第 6 节）。

## 1. 登录和人员

### 登录

- 只用 Google 登录（D-A3）。登录页只有一个按钮「用 Google 登录」。
- 后端校验 Google 的 ID token（邮箱必须已验证），再查 `admins` 表：
  - 在表里且启用 → 进后台；
  - 不在表里或已停用 → 停在登录页，显示「这个 Google 账号没有后台权限。需要的话，请联系负责人。」
- 一个邮箱第一次登录时，记下它的 Google 账号编号（`sub`）。以后用同一个邮箱登录，编号必须一样，不一样也按「没有权限」处理。这样邮箱换了主人也登不进来。不按 Google Workspace 的域名限制，个人 Gmail 也能登。
- **登录限流：** 10 分钟内所有人加起来登录失败超过 30 次，后端暂停登录，显示「登录尝试太多了，请稍后再试。」
- 会话放在 httpOnly cookie（`__Host-psygym_admin`）里，7 天。每次请求都重查 `admins` 表，停用当场生效。
- 登录日志只记人员和时间，留 90 天（admin.md 第 5 节）。
- **风险（照 admin.md 第 4 节）：** 聆镜的同事在国内可能打不开 Google 登录页。上线后先请他们试一次；登不上就加邮件验证码登录（约一两天的工作量）。

### `admins` 表

| 字段 | 说明 |
|------|------|
| 邮箱 | 小写，唯一。就是 Google 账号的邮箱。 |
| 角色 | 管理员 / 编辑 / 只读 |
| 来自 | Novawerk / 聆镜 |
| 是否启用 | 停用后立即登不进来，已登录的下一次请求就被踢出 |
| Google 账号编号（`google_sub`） | 第一次登录时记下，以后登录必须一致。用命令加人时是空的。 |
| 创建时间、最近登录时间 | |

### 角色能做什么

| | 管理员 | 编辑 | 只读 |
|--|:--:|:--:|:--:|
| 看数据看板 | ✓ | ✓ | ✓ |
| 看病例、督导标准、版本历史、发布记录 | ✓ | ✓ | ✓ |
| 新建、改草稿、试聊 | ✓ | ✓ | |
| 发布、回滚 | ✓ | ✓ | |
| 管理后台人员 | 第二期（第一期用命令） | | |

- 没有权限的按钮**不显示**，不是灰掉。只读的人进编辑页，看到的是只读视图，顶上一行「你是只读角色，不能修改。」
- 聆镜的心理学同事默认是「编辑」。
- 建议所有编辑和管理员开启 Google 账号的两步验证（admin.md D-A9 的风险）。离开项目的人当天停用。

### 第一位管理员怎么开

第一期没有人员管理页面，所有人都用后端的一条命令加：

```bash
pnpm --filter api admin:add --email <邮箱> --role admin --org novawerk
```

- `--org` 是 `novawerk` 或 `lingjing`。邮箱已经在表里时，这条命令改角色并重新启用；停用用 `admin:disable --email <邮箱>`。命令连生产库时，用和数据库迁移一样的方式（`vercel env run …`），不在本地存密钥。
- 第一位管理员由我们指定的成员开。聆镜的同事由我们按他们给的邮箱加，角色「编辑」。
- 第二期做人员管理页面以后，命令仍然保留，作为兜底。

## 2. 页面结构

桌面为主（1280 宽），照 Novawerk 后台的结构：shadcn base-vega，zinc 配色，浅色和深色都要。手机能打开、能看数据，编辑不专门适配。

- **左侧栏：** 聆镜 PSYGYM 后台（标志）/ 数据看板 / 病例 / 督导标准 / 发布记录。底部：当前邮箱、角色、退出。
- **顶栏：** 面包屑；右边主题切换。
- 默认进「数据看板」。

## 3. 数据看板

### 筛选

- 日期范围：最近 7 天 / 最近 30 天（默认）/ 最近 90 天 / 自定义。日期按 UTC。
- 粒度：按天 / 按周（ISO 周，周一到周日）。
- 病例：全部 / 每个病例（显示中文标题）。
- 语言：全部 / 中文 / 英文。
- 筛选和按周汇总**都在后端做**，<5 规则套在筛选后的结果上。前端不能把带「<5」的格子自己加起来。

### 数字卡（顶上一排）

所选范围的合计：

| 卡片 | 来自 |
|------|------|
| 开始的会谈 | `session_started` |
| 完成的会谈 | `report_generated`（生成了完整报告） |
| 完成率 | 完成 ÷ 开始；任一边是「<5」时显示「—」 |
| 实时督导 | `live_supervision` |
| 👍 比例 | 👍 ÷（👍 + 👎）；任一边是「<5」时显示「—」 |
| 日活 / 周活 | `active_day` 的日均、`active_week` 最近一周；带病例或语言筛选时显示「筛选时不可用」 |

### 图和表

| 图 | 内容 |
|----|------|
| 会谈（折线） | 开始、来访者主动结束、完成、报告失败、实时督导 |
| 活跃人数（折线） | 日活、周活。只按全部算，不受病例和语言筛选影响（带筛选时整张图显示「筛选时不可用」） |
| 评价和举报（柱状） | 👍、👎；举报按原因分 |
| 出错（柱状） | 按错误码分 |
| 时长分布（柱状） | 0–5、5–10、10–20、20–40、40 分钟以上，外加平均时长。场数是「<5」时平均时长显示「—」 |
| 轮数分布（柱状） | 1–5、6–15、16–30、31+ |

- 每张图下面有「显示表格」，展开是同样的数：行是日期（或周），列是指标。
- **「<5」原样显示。** 表格里写「<5」；折线在这个点断开，悬停提示「少于 5，不显示具体数字」。不画成 0。
- 看板底部一行说明：「为保护隐私，少于 5 的数字显示为 <5；同一行或同一列只遮一个数时，会多遮一个。日活周活是按天、按周轮换的假名统计。」
- 第一期不做导出。

## 4. 病例和督导标准

病例和督导标准用同一套页面，下面写病例，督导标准只写不一样的地方。

### 列表

| 列 | 说明 |
|----|------|
| 标题 | 中文标题，下面一行灰字是 id |
| 已发布版本 | v3；从没发布过的显示「未发布」 |
| 发布时间 | |
| 草稿 | 有草稿时显示「有草稿」和最后修改时间 |
| 提示 | 「英文缺失」：title、summary 或 clientIntro 的英文是空的 |

右上角「新建病例」（编辑、管理员可见）：填 id（小写英文、数字、连字符，定了不改）和流派（第一期只有 CBT），建一份空草稿，内容按 `content/README.md` 的模板预填。

### 编辑页

**顶栏：** 标题、id、状态（「已发布 v3」「有未发布的草稿」）；按钮：版本历史、预览、保存草稿、发布。

**第一部分：卡片信息（中英并排）。** 左边中文、右边英文，一行一个字段，字段照 `content/README.md`：

| 字段 | 控件 | 规则（后端校验） |
|------|------|------------------|
| 标题 title | 单行 | 必填；中文 10 字以内，英文 40 字符以内 |
| 简介 summary | 两行 | 必填 |
| 化名 clientAlias | 单行 | 可选 |
| 主题标签 tags | 标签输入 | 可选，最多 3 个 |
| 难度 difficulty | 下拉：入门 / 中等 / 较难 | 可选；中英不分开 |
| 预计时长 estimatedMinutes | 数字，分钟 | 可选；中英不分开 |
| 来访者 clientIntro | 多行 | 可选 |
| 这次练什么 practiceFocus | 列表，1–3 条 | 前两条固定「风险筛查」「判断能不能承接」，第三条可选 |
| 内容提示 contentNotes | 多行 | 可选；空着用通用提示 |

- 英文可以空着，空着时 App 英文界面显示中文。英文空着的字段旁边标「英文缺失」，不拦发布。
- 字段旁的小字提示照搬 `content/README.md` 的说明，例如化名「像真人的常见称呼，不写全名」。
- 页面上方常驻一句：「这些都是学员开始会谈前就能看到的内容。不要写核心信念和『不会轻易透露』的内容。」

**第二部分：给 AI 的角色说明（正文）。** 一个 Markdown 编辑器，只写中文（AI 读）。右边是大纲，列出模板的小标题（来访者基本情况、主诉、症状表现……），缺的标灰。HTML 注释（例如「临时版本，待聆镜确认」）原样保留，编辑器里用灰底显示。

**校验：** 保存草稿时就校验。不合格也能存草稿，但不能发布；错误标在字段旁边，顶上汇总「有 2 处要改」，点了跳过去。

**两个人同时改：** 每个病例只有一份草稿。保存时如果别人在这之间存过，提示「草稿已被 <邮箱> 在 <时间> 修改。复制你的改动，刷新后再改。」不自动合并。

**离开页面：** 有没保存的改动时，提示「有改动还没保存，确定离开吗？」

### 预览

点「预览」，右侧打开面板，两个标签：

1. **卡片：** 用草稿内容画出 App 的病例卡片和病例简介页（中文 / 英文切换），样子和 App 一致。
2. **试聊：** 用草稿当角色说明，和 AI 来访者聊几句，看演得对不对。
   - 顶上一行：「试聊用的是草稿，不保存，不计入统计。」
   - 可以选界面语言（中文 / 英文），有「重新开始」。
   - 不出督导报告，不出实时督导。
   - 按人限流（每人每小时 60 轮），到了提示「试聊太频繁了，过一会儿再试。」

**为什么试聊放第一期：** 改病例的人看不到 AI 实际怎么演，就只能发布以后在 App 里试，演错了已经影响到用户。试聊用的是现有的 `/chat` 流程，换一份角色说明而已，工作量小。

督导标准的预览只显示渲染后的文字，第一期不做「拿一段对话试评」。

### 发布

- 点「发布」弹确认框：
  - 标题：「发布 cbt-depression-anxiety-01 v4？」
  - 正文：「App 会在一分钟内用上这个版本。发布会记录在发布记录里，并在 Slack #project-psygym 发一条通知。」
  - 「改了什么」输入框（可选），写进发布记录，不发到 Slack。
  - 按钮：取消 / 发布。
- 校验不通过时，「发布」按钮不能点，悬停提示「先改完标出的问题」。
- 发布时如果有人刚发布过新版本（页面还停在旧版本），提示「这期间有人发布了 v4。刷新后再发布。」
- **草稿落后了：** 草稿是在 v3 上改的，这期间有人发布或回滚出了 v4，发布会被拦下（不会用旧草稿盖掉别人的改动）。页面提示「你的草稿是在 v3 上改的，这期间有了 v4。先看 v4 改了什么，把需要的改动合进草稿，再发布。」，两个按钮：
  - 「看 v4 改了什么」：打开版本历史里 v4 和 v3 的差异；
  - 「已合并，更新草稿」：把草稿的起点改成 v4（后端的 `rebase`），然后再点发布。
  - 不自动合并：两边改了同一处，只有人能判断留哪个。
- 发布后：草稿清空，状态变「已发布 v4」，顶上提示「已发布 v4」。

### 版本历史和回滚

点「版本历史」打开右侧抽屉：

- 每一行：版本号、发布时间、发布人邮箱、操作（发布 / 回滚到 vN）、「改了什么」。
- 点一行看那一版的全文，以及和当前已发布版的差异（逐行对比）。
- 「恢复成这个版本」（编辑、管理员可见）：弹确认框「把 v2 的内容发布成 v5？App 会在一分钟内用上。有草稿的话，草稿会落后于新版本，要先「已合并，更新草稿」才能发布。」恢复也是一次发布，版本号加 1，同样留痕、同样发 Slack。
- 旧版本不符合现在的校验规则时（例如规则后来变严了），不能直接恢复，提示「v2 不符合现在的校验规则，不能直接恢复。把需要的内容复制进草稿，改好后再发布。」
- 当前版本那一行没有「恢复」按钮。旧版本永远不删。

### 发布记录

侧栏「发布记录」：所有病例和督导标准的发布、回滚，按时间倒序。

| 列 | 说明 |
|----|------|
| 时间 | |
| 类型 | 病例 / 督导标准 |
| id 和版本 | 点了跳到那个版本 |
| 操作 | 导入 / 发布 / 回滚到 vN |
| 发布人 | 邮箱和角色；切换日导入的 v1 显示「导入」，没有发布人 |
| 改了什么 | |

### Slack 通知

发布和回滚各发一条到 #project-psygym。**只写类型、id、版本号、操作和角色，不写人名，不写内容。**

- 发布：`病例 cbt-depression-anxiety-01 发布了 v4（编辑）`
- 回滚：`督导标准 cbt 回滚到 v2，生成 v5（管理员）`

Slack 发不出去不影响发布，后端打一行日志。webhook 放在后端环境变量 `CONTENT_SLACK_WEBHOOK_URL`，没设时只打日志。

### 督导标准不一样的地方

- 卡片信息只有标题（中英）。
- 正文同样是一个 Markdown 编辑器，大纲照 `content/README.md` 第 2 节（这份标准适用于、要看的点、新手常见错误……）。
- 预览只有文字，没有试聊。
- 不能新建（第一期只有 CBT 一份）。

## 5. 后端怎么读（照 admin.md，不变）

App 每次请求读已发布的最新版本，后端缓存 1 分钟；数据库连不上时用上一次读到的；刚启动就连不上时用打包的 `content/` 兜底。草稿从来不进 App。

## 6. 上线那天（切换日）

按后端 ADR 0009 的顺序：

1. 先把还开着的、改 `content/cases/` 或 `content/rubrics/` 的 PR 合完或关掉。
2. 数据库迁移，部署后端。
3. 用命令开第一位管理员，打开后台开关（`ADMIN_MODE=on`）。
4. 用后端的 `content:import` 命令把现有文件导入数据库，每个病例和督导标准记为「v1，已发布」，发布记录里记作「导入」。导入用后端的校验规则，有一个文件不合格就整批停下，人工处理。导入后在后台逐个打开，确认内容和文件一致；用试聊各聊几句。
5. 打开后端开关，让 App 改从数据库读（`CONTENT_SOURCE=db`）。关着时 App 照旧读打包的 `content/`，可以随时退回。
6. 同一天更新 `content/README.md` 和 `docs/for-psygym-team.md`：病例和督导标准以后在后台改，仓库里的文件是导出的副本，提 PR 改不会生效。

**第二期同步上线之前：**

- 数据库是来源。每次发布后，由我们用后端的 `content:export` 命令把已发布版本导出成 `content/` 下的文件，开 PR 更新。导出的文件和现在的格式一字不差。Slack 的发布通知就是提醒。
- 这段时间还没有 CI 锁。PR 审查时，人手改 `content/cases/` 或 `content/rubrics/` 的 PR 一律不合，请提的人改到后台去。

## 7. 接口约定（和后端对齐用）

正式的接口见 [`docs/decisions/0009-admin-phase1.md`](../decisions/0009-admin-phase1.md) 和 [`docs/admin-api.md`](../admin-api.md)，有出入时以它们为准。下面是对齐后的形状：

| 接口 | 用途 |
|------|------|
| `POST /admin/auth/google`、`POST /admin/auth/logout`、`GET /admin/me` | 登录、退出、当前人员（邮箱、角色、来自） |
| `GET /admin/dashboard?from&to&granularity=day\|week&caseId&locale` | 看板。现有的 `GET /admin/stats`（Bearer token）不变 |
| `GET /admin/content?kind=case\|rubric` | 列表 |
| `GET /admin/content/:kind/:id` | 已发布版和草稿 |
| `POST /admin/content` | 新建（只建草稿） |
| `PUT /admin/content/:kind/:id/draft`、`DELETE …/draft` | 存草稿（返回校验错误）、放弃草稿 |
| `POST /admin/content/:kind/:id/publish` | 发布（校验不过 422；页面上的版本过时 409；草稿起点不是当前版本 409 `draft_outdated`） |
| `GET /admin/content/:kind/:id/versions`、`GET …/versions/:v` | 版本历史、某一版全文 |
| `POST /admin/content/:kind/:id/rollback` | 恢复成某个旧版本（生成新版本；旧版本不过现在的校验 422） |
| `POST /admin/content/case/:id/preview-chat` | 试聊：和 `/chat` 一样的流，用草稿当角色说明，不计数、不存 |
| `GET /admin/publish-log` | 发布记录 |

- **地址：** `admin.psygym.novawerk.io`。后台用 Vercel rewrite 把 `/api/*` 转到 `psygym-api`，同源 cookie `__Host-psygym_admin`。非 GET 请求后端检查来源和 JSON 格式。本地开发用 Vite 代理。
- **存储：** 每个版本存整份 `.md` 原文，保证导出一字不差（YAML 注释和顺序都留着）。接口同时给解析后的字段、正文和原文；存草稿时前端发字段和正文，后端合回原文。
- **并发：** 草稿带一个修订号。存草稿、放弃草稿、发布都带上它，对不上返回 409（第 4 节「两个人同时改」）。发布另带当前已发布的版本号，对不上也是 409。草稿的起点不是当前已发布版本时，发布返回 409 `draft_outdated`；看过新版本、合好以后，存草稿时带 `rebase: true` 把起点移到当前版本（第 4 节「草稿落后了」）。
- **看板：** 筛选、按周汇总、<5 遮挡都在后端。遮挡按「指标 × 时间段 × 细分」的表，行和列都防反推。周按 ISO 周（周一开始，UTC），用周一的日期表示一周。分档（时长、轮数等）和它们的总数放在一起遮，所以时长的场数也可能显示「<5」，这时平均时长显示「—」。
- **试聊：** 流格式同 `/chat`，不计数、不存、不发 Slack，每人每小时 60 轮，只给编辑和管理员。
- **发布记录** 的操作有三种：导入、发布、回滚。
- **开关：** `ADMIN_MODE=on` 打开后台接口（关着时新接口 404）；`CONTENT_SOURCE=db` 单独打开 App 从数据库读内容。
- **Slack：** `CONTENT_SLACK_WEBHOOK_URL`，值由我们在 Slack 建好后设置，不进仓库。

## 8. 第二期：GitHub 单向同步要我们做的事

同步方案见 admin.md 第 2 节「同步步骤」。代码之外，要我们（有 GitHub 组织管理权限的人）做这几步：

1. **建 GitHub App**：组织设置 → Developer settings → GitHub Apps → New。名字例如 `psygym-content-sync`；不要 webhook；权限只给 Contents（读写）、Pull requests（读写）、Metadata（只读）。
2. **只装在本仓库**：Install App → Only select repositories → `project-psygym-workspace`。
3. **生成私钥**：App 页面 → Generate a private key，下载 `.pem`。把 App ID、安装 ID 和私钥设成后端的环境变量（名字由后端定）。私钥不进仓库，设完删掉本地文件。
4. **分支保护**：main 要求 PR 和必过检查，不给这个 App 绕过权限；把「`content-sync` 的 PR 只能改 `content/cases/` 和 `content/rubrics/`」和「人改这两个目录就失败」两个检查设为必过。
5. **允许自动合并**：仓库设置里打开 Allow auto-merge。

## 10. 验收

- [ ] 不在 `admins` 表里的 Google 账号登不进；停用后下一次请求被踢回登录页。
- [ ] 只读角色看不到新建、保存、发布、恢复按钮；直接调接口也被拒。
- [ ] 看板（不带筛选、按天）的数字和 `GET /admin/stats` 同一范围的数一致；「<5」不画成 0；带筛选时日活周活显示「筛选时不可用」。
- [ ] 按周汇总时，后端出的「<5」和防反推规则正确（同一行或同一列只遮一个时多遮一个）。
- [ ] 存草稿后 App 里看不到改动；发布后一分钟内 App 用上新版本。
- [ ] 校验不过不能发布，错误标在字段旁。
- [ ] 试聊用的是草稿；试聊不计入看板。
- [ ] 回滚生成新版本，App 用上旧内容，草稿不动；旧版本不过现在的校验时提示，不发布。
- [ ] 草稿起点落后时发布被拦，合并并「更新草稿」后能发布；不会用旧草稿盖掉别人的版本。
- [ ] 同一个邮箱换了 Google 账号登不进；10 分钟内失败登录超过 30 次显示限流提示。
- [ ] 每次发布和回滚，Slack #project-psygym 各一条，只有类型、id、版本号、操作、角色。
- [ ] 发布记录和版本历史里能查到谁、什么时候、哪个版本。
- [ ] 导出命令导出的文件和导入前的 `content/` 一字不差（导入后什么都没改时）。
- [ ] 浅色、深色都对；1280 宽不出横向滚动条。
