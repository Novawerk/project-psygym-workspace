# 后台方案

**状态：方案，待定。** 先写清楚要做什么、怎么做、要定什么，不写代码。要拍板的点集中在文末「要定的事」。

## 一句话

一个只给 Novawerk 和聆镜的人用的网页后台：看匿名的使用指标、管理邀请码、管理病例。服务端不存对话，这一条不变。

## 现在是什么样

- 后端（`apps/api`，Hono，Vercel fra1）**完全无状态**：没有数据库，没有 KV。日志只记 id、枚举、长度、耗时，从不记正文。
- 邀请码是环境变量 `INVITE_CODES` 里的一串码。码不对应任何人，只用作限流的 key。加码、作废都要改环境变量、重新部署。
- 病例是 `content/cases/*.md`，构建时打进后端，启动时读一次。聆镜通过 PR 改。
- 反馈（👍/👎）和举报转发到我们内部的 Slack 频道，不进数据库。

## 参考：Novawerk 的 `apps/admin`

我们照它的结构做，能抄的直接抄：

- **前端：** React 19 单页应用，Vite+ 构建，TanStack Router（按文件生成路由）+ TanStack Query。
- **数据：** 用 Hono 类型化客户端调自己的 API。真实数据和假数据两套实现，`VITE_USE_SAMPLE_DATA` 切换。
- **UI：** shadcn base-vega。侧栏 + 顶栏 + ⌘K；带分页排序的数据表、表单、确认弹窗。
- **登录：** 只有 Google 登录。后端校验 Google ID token，查 `members` 表决定能不能进。会话放在 httpOnly cookie 里（JWT，7 天），每次请求都重查权限，撤销立即生效。**没有邮件验证码登录**，要做得新加。
- **存储：** Postgres（Neon，法兰克福）+ Drizzle；Vercel fra1。

## 1. 指标：看什么、怎么采、存在哪

### 原则

- **只存计数，不存事件明细，不存任何文字。** 不存对话、报告、反馈的那句话、举报的原文（这些仍然只走 Slack）。
- **不给用户发任何 ID。** 没有设备 ID、没有安装 ID、不存 IP。所以我们只知道「发生了几次」，不知道「是几个人」。
- 计数失败绝不影响请求：写计数是「发出去就不管」，出错只打一行日志。

### 看什么

按 **天（UTC）× 病例 × 界面语言** 计数：

| 指标 | 怎么算（在后端哪一步加 1） |
|------|---------------------------|
| 开始的会谈 | `/chat` 请求里只有一条消息（咨询师的第一句） |
| 对话轮数 | 每次 `/chat` 成功 |
| 来访者主动结束 | 流里发了 `session_end` |
| 生成的报告 | `/supervision` 成功结束 |
| 报告生成失败 | `/supervision` 出错 |
| 👍 / 👎 | `/feedback` 的 rating |
| 举报 | `/report`，按原因分 |
| 出错 | 按错误码分：`invite_required`、`rate_limited`、`model_unavailable`、`case_not_found`、`invalid_request`、流中出错 |
| 一场的轮数 | `/supervision` 时对话有几条消息，记分布（1–5、6–15、16–30、31+ 四档） |

后台里能算出来的：完成率（报告数 ÷ 开始数）、每场平均轮数、👍 比例、出错率。

**时长：** 服务端无状态，不知道一场聊了多久。要看时长，得让 App 在 `/supervision` 里多带一个 `durationSec`（只是一个数字），要改合同。见「要定的事」D-A4。

**用户数：** 只靠计数算不出来。邀请码算不算「用户」，见下一节和 D-A1。

### 邀请码算不算「用户」

邀请码是一串共享的码，不是账号：

- 一个码可能给了一个人，也可能给了一整个班。
- 同一个人可以在两台手机上用同一个码。

所以「每个码的用量」只能说明「这批人用得多不多」，不能当成用户数。

如果要按码看用量，计数里就多一个维度「邀请码」。码最好按批次发（例如「聆镜内测第一批」），不要一人一码。一人一码时，按码计数就能对应到具体的人，变成了个人数据。

### 存在哪

| 选项 | 说明 |
|------|------|
| **Postgres（Neon 法兰克福）+ Drizzle** | 和 Novawerk 主仓库同一套，后面邀请码、病例、登录都要数据库，一步到位。一张表 `daily_counts(day, metric, case_id, locale, dim, count)`，写的时候用 upsert 加 1。 |
| Upstash Redis（欧盟） | 计数写起来最简单。但后面的邀请码、病例、登录还是要关系库，等于要两套。 |

**建议：Postgres（Neon 法兰克福）。**

## 2. 病例管理

现在：病例是 GitHub 里的 Markdown 文件，聆镜改要开 PR，我们审、合并、部署。好处是有版本、有审核、全公开；坏处是心理学同事不熟 GitHub。

| 选项 | 怎么做 | 利 | 弊 |
|------|--------|---|---|
| A. 只用 GitHub（现状），后台只读 | 后台列出病例、预览中英文、显示校验结果，「去 GitHub 改」按钮 | 不用新东西；版本和审核都是 git 的 | 聆镜还是得会 PR，或者发给我们改 |
| B. 后台编辑，存数据库 | 后台表单编辑（中英并排），草稿 → 送审 → 发布；每次发布存一个版本，能回滚；后端从数据库读已发布版本 | 聆镜自己能改，即改即生效 | 病例离开了 GitHub，不再公开、不再走 PR；要自己做版本、审核、回滚；和「open by default」相冲 |
| C. 后台编辑，后台替你开 PR | 后台表单编辑（中英并排，实时校验），点「提交」时后台用 GitHub API 开一个 PR；我们或聆镜的另一位同事在 GitHub 上审、合并；合并后自动部署 | 聆镜不用懂 Git；版本、审核、公开都还是 git 的；两种方式并存（会 Git 的直接改文件） | 改了不是马上生效，要等合并和部署（几分钟）；后台要有一个 GitHub App 或 token |

**两种都留可以吗？** 用 C 就是两种都留：文件仍是唯一的真相，后台只是一个更好用的编辑器。用 B 时不能两边都改，否则会冲突。

**建议：C。** 中英两版放在同一份文件里，后台并排编辑。英文可以空着，空着时 App 显示中文（现有规则）。审核规则：病例和督导标准的改动，至少一位聆镜心理学同事在 PR 里同意，这一条写进 PR 模板。

同样适用于督导标准 `content/rubrics/cbt.md`。

## 3. 邀请码管理

把邀请码从环境变量搬进数据库：

| 字段 | 说明 |
|------|------|
| 码 | 随机生成，8–10 位，去掉易混的字符。存哈希；明文只在生成时显示一次。 |
| 名称 | 例「聆镜内测第一批」「10/18 demo 会」 |
| 创建人、创建时间 | |
| 有效期（可选） | 过期自动失效 |
| 作废时间 | 作废后立即生效（后端每次请求查表，加 1 分钟缓存） |

后台能做：新建（可以一次建多个）、改名称、作废、看每个码每天开始了几场、生成了几份报告（就是第 1 节的计数加一个「码」维度）。

限流仍按码，但每个码的上限可以在后台调。

## 4. 谁能登录、怎么登录

- **只给 Novawerk 和聆镜的人。** 一张 `admins` 表：邮箱、角色、来自哪边（Novawerk / 聆镜）、是否启用。不在表里的邮箱登不进来。
- **角色：**
  - 管理员：管理人员和邀请码。
  - 编辑：改病例，开 PR。
  - 只读：看指标。
  - 聆镜的心理学同事默认是「编辑」。
- **登录方式：**
  - Google 登录：照抄 Novawerk。
  - 邮件验证码：Novawerk 没有，要新做。用 Resend（爱尔兰）发 6 位码，10 分钟有效。
  - **聆镜的同事在中国大陆，可能用不了 Google**，所以邮件验证码很可能是必需的。见 D-A3。
- 会话：httpOnly cookie，7 天；每次请求重查 `admins` 表，停用立即生效。
- 放在哪：见 D-A2。

## 5. 隐私

- **存在哪：** 数据库 Neon 法兰克福，后端和后台 Vercel fra1，验证码邮件 Resend 爱尔兰。都在欧盟。
- **存什么：**
  - 按天的匿名计数：不含任何 ID、IP、文字，不算个人数据。
  - 邀请码的哈希和名称。
  - 后台管理员的邮箱和登录记录：这是我们自己成员的个人数据。
- **保留多久：**
  - 计数：一直留（没有个人数据，留着才能看趋势）。
  - 后台登录日志：90 天。
  - 验证码：用完或过期就删。
  - 反馈和举报：仍只在 Slack，不进数据库。
- **要改的文档：**
  - `docs/safety.md` §1 加一条：「后端按天统计匿名次数（开始、完成、出错等），不含对话、不含任何能认出用户的信息。」
  - 隐私政策（`docs/release/privacy-policy.md`）和 App 里的隐私说明（P3）加一问「你们统计什么？」。
  - 商店的隐私标签（`docs/release/privacy-labels.md`）要请发布成员核对：匿名、不关联用户的使用统计怎么填。
- **和 Novawerk 一样待办：** 和 Neon、Vercel、Resend 签数据处理协议（DPA）。

## 6. 分期

| 期 | 做什么 | 不做什么 |
|----|--------|----------|
| **demo 前（10/17 前）** | 只开始**匿名计数**：建库、建 `daily_counts` 表、后端在上面列的几个点加 1；有开关可以随时关掉。没有后台界面，要看数就用一个受保护的 `GET /admin/stats`（用一个密钥），或者直接查库。safety §1、隐私说明加一句。 | 不做后台界面、登录、邀请码搬家、病例编辑 |
| **Epic 2（圣诞前）** | 后台网页：登录、指标看板（按天、病例、语言的折线和表格）、邀请码管理、病例编辑（选 C 时开 PR）、管理员管理 | 不做用户账号、不做用户级数据 |

**为什么 demo 前就开始计数：** 没采的数据补不回来，demo 前后正是第一批真实使用。

**风险：** 离 demo 一周给后端加数据库，所以计数一律「发出去就不管」，出错不影响请求，并且有环境变量开关。数据库挂了，App 照常用。
