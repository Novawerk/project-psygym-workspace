# 后台方案

**状态：定稿（2026-10-11）。** D-A2–D-A8 已定，见文末「决定」；D-A1、D-A9、D-A10 还要定。还没写代码。

## 一句话

一个只给 Novawerk 和聆镜的人用的网页后台：看匿名的使用指标、管理邀请码、管理病例。服务端不存对话，这一条不变。

## 现在是什么样

- 后端（`apps/api`，Hono，Vercel fra1）**完全无状态**：没有数据库，没有 KV。日志只记 id、枚举、长度、耗时，从不记正文。
- 邀请码是环境变量 `INVITE_CODES` 里的一串码。码不对应任何人，只用作限流的 key。加码、作废都要改环境变量、重新部署。
- 病例是 `content/cases/*.md`，构建时打进后端，启动时读一次。聆镜通过 PR 改。
- 反馈（👍/👎）和举报转发到我们内部的 Slack 频道，不进数据库。

## 参考：Novawerk 的 `apps/admin`

我们照它的结构和做法来做。本仓库是公开的，Novawerk 主仓库是私有的：只借鉴结构、选型和做法，不把私有仓库的内部代码细节直接搬过来，需要的部分在本仓库重新写。

- **前端：** React 19 单页应用，Vite+ 构建，TanStack Router（按文件生成路由）+ TanStack Query。
- **数据：** 用 Hono 类型化客户端调自己的 API。真实数据和假数据两套实现，`VITE_USE_SAMPLE_DATA` 切换。
- **UI：** shadcn base-vega。侧栏 + 顶栏 + ⌘K；带分页排序的数据表、表单、确认弹窗。
- **登录：** Google 登录和邮件验证码登录都有。后端校验 Google ID token，或者校验发到邮箱的一次性验证码；再查成员表决定能不能进。会话放在 httpOnly cookie 里，每次请求都重查权限，撤销立即生效。
- **存储：** Postgres（Neon，法兰克福）+ Drizzle；Vercel fra1。

## 1. 指标：看什么、怎么采、存在哪

### 原则

- **只存计数，不存事件明细，不存任何文字。** 不存对话、报告、反馈的那句话、举报的原文（这些仍然只走 Slack）。
- **不给用户发任何 ID。** 没有设备 ID、没有安装 ID、不存 IP。所以我们只知道「发生了几次」，不知道「是几个人」。
- 计数失败绝不影响请求：写计数是「发出去就不管」，出错只打一行日志。

### 看什么

按 **天（UTC）× 病例 × 界面语言** 计数。

**先清洗再计数：** 病例和语言来自请求，用户可以随便写。写进数据库之前：`caseId` 不在已知病例里就记成 `unknown`；`locale` 只收 `zh` 和 `en`，其他一律记成 `unknown`。这样数据库里不会出现用户写的任意字符串。


| 指标 | 怎么算（在后端哪一步加 1） |
|------|---------------------------|
| 开始的会谈 | `/chat` 请求里只有一条消息（咨询师的第一句） |
| 对话轮数 | 每次 `/chat` 成功 |
| 来访者主动结束 | 流里发了 `session_end` |
| 生成的报告 | `/supervision` 成功结束 |
| 报告生成失败 | `/supervision` 出错 |
| 👍 / 👎 | `/feedback` 的 rating |
| 举报 | `/report`，按原因分 |
| 出错 | 按错误码分：`invite_required`、`rate_limited`、`model_unavailable`、`case_not_found`、`invalid_request`、流中出错 |
| 一场的轮数 | `/supervision` 时对话有几条消息，记分布（1–5、6–15、16–30、31+ 四档） |
| 一场的时长（D-A4，已定） | `/supervision` 请求里 App 带上的 `durationSec`，见下 |

后台里能算出来的：完成率（报告数 ÷ 开始数）、每场平均轮数、平均时长、👍 比例、出错率。

**时长怎么采（D-A4 = B）：**

- App 在 `/supervision` 的请求体里多带一个可选的整数 `durationSec`：从第一句发出到点「结束并查看督导」的秒数。来访者主动结束时，算到收到 `session_end` 那一刻（见走查 #C）。
- 只是一个数字，不带时间戳，不带任何 ID。后端校验范围（0–7200 秒），超出就丢掉，不报错。
- 后端只存聚合：每个「天 × 病例 × 语言」格子累加「总秒数」和「场数」，另记时长分布（0–5、5–10、10–20、20–40、40 分钟以上五档）。不存单场的时长。
- 要改合同（`api-contract.md`），后端和 App 在同一个 PR 里改。旧版 App 不带这个字段，照常处理。

**最小展示阈值：** 内测期人少，按码或按病例细分后，某天的数可能只有 1 或 2，能对应到具体的人。规则：

- 任何格子小于 5 就显示「<5」，不显示具体数字。
- **防反推：** 一行（或一列）里如果只有一个格子被遮，用合计一减就能算出来。所以这种情况下，再遮住同一行（或列）里第二小的格子。合计照常显示。
- 后台页面、导出、`GET /admin/stats` 都套用同一条规则，在后端做，不靠前端。

**用户数：** 只靠计数算不出来。邀请码算不算「用户」，见下一节和 D-A1（待定）。

### 邀请码算不算「用户」

邀请码是一串共享的码，不是账号：

- 一个码可能给了一个人，也可能给了一整个班。
- 同一个人可以在两台手机上用同一个码。

所以「每个码的用量」只能说明「这批人用得多不多」，不能当成用户数。

如果要按码看用量，计数里就多一个维度「邀请码」。码最好按批次发（例如「聆镜内测第一批」），不要一人一码。一人一码时，按码计数就能对应到具体的人，变成了个人数据。选了按码统计，隐私说明里「服务器不保存邀请码」要改成「只存邀请码的哈希，用来统计各批次的用量」。

### 存在哪（D-A7 = A，已定）

Postgres（Neon 法兰克福）+ Drizzle，和 Novawerk 主仓库同一套选型。计数一张表 `daily_counts(day, metric, case_id, locale, dim, count)`，时长一张表 `daily_durations(day, case_id, locale, total_sec, sessions, bucket_*)`，写的时候用 upsert 累加。

## 2. 病例管理（D-A5 = B，已定：后台编辑，存数据库）

我们定了：病例在后台编辑，数据库是病例的来源。这一节写清楚怎么过渡、GitHub 里的 `content/` 怎么办、版本和审核怎么做。

### 数据库里存什么

- **病例：** 一行一个病例（`id` 定了不改），加上版本表。每个版本存完整的病例内容：frontmatter 里的所有字段（中英并排）和正文（给 AI 的角色说明）。
- **督导标准：** 一样存数据库，一样有版本。见 D-A10（待定）。
- **校验：** 保存时用后端现有的病例校验规则（必填字段、可选字段格式）。不合格不能送审，后台当场标出哪里不对。

### 版本和审核

| 状态 | 谁能做 | 说明 |
|------|--------|------|
| 草稿 | 编辑 | 随时改，只有后台看得到，App 看不到。 |
| 待审 | 编辑点「送审」 | 草稿冻结，等审核。 |
| 已发布 | 审核人点「发布」 | 成为一个新版本，版本号加 1，记下谁改的、谁审的、什么时候。App 从下一次请求起用新版本（后端缓存 1 分钟）。 |
| 退回 | 审核人 | 回到草稿，附一句理由。 |

- **回滚：** 在版本列表里选一个旧版本，点「恢复成这个版本」。这会生成一个新的待审版本，照常审核、发布。旧版本永远不删。
- **审核规则：** 见 D-A9（待定）。建议：病例和督导标准是临床内容，至少一位聆镜的心理学同事审核通过才能发布，并且审核人不能是改的人。
- **中英两版：** 同一个版本里中英并排编辑。英文可以空着，空着时 App 英文界面显示中文（现有规则）。后台列表里标出「英文缺失」的病例。
- **后端读取：** 后端从数据库读已发布的最新版本，在内存里缓存 1 分钟。数据库连不上时，用上一次成功读到的版本；进程刚启动就连不上时，用打包进去的 `content/` 文件兜底。
  - 打包的 `content/` 跟着每次发布的导出更新（D-A8 = B），兜底时用的也是较新的版本；导出没跟上时，最多落后于未同步的那几次发布。
  - **会谈中途病例换了版本：** 后端无状态，每一轮都读当时的已发布版本。所以一场会谈中途如果发布了新版，后面几轮来访者按新版演。督导不读病例的角色说明（只读对话），只按病例的流派挑用哪份督导标准；流派一般不会变，所以基本不受影响。发布不频繁，影响很小，我们接受；以后要严格的话，可以让 App 在请求里带上开始时的版本号。

### GitHub 里的 `content/`（D-A8 = B，已定：单向同步）

方向只有一个：**后台（数据库）→ GitHub**。数据库是病例和督导标准的来源；仓库里的 `content/` 是已发布版本的公开副本，由机器人维护，人不再手改。这样开源仓库一直能看到已发布的病例，git 历史就是发布历史，后端兜底用的打包文件也一直是新的。

### 同步步骤

**1. 切换日（后台病例编辑上线那天，做一次）**

1. 先把还开着的、改 `content/` 的 PR 合完或关掉。
2. 把 `content/cases/*.md` 和 `content/rubrics/*.md` 导入数据库，每个病例和督导标准记为「版本 1，已发布」。导入用后端现有的校验规则，不合格的停下来人工处理，不跳过。
3. 导入后马上打开 CI 检查：任何人提交的改动只要碰到 `content/cases/` 或 `content/rubrics/`，检查失败、不能合并。只放行同步机器人。`content/README.md` 不锁，用来写说明。
4. 同一天更新 `content/README.md` 和 `docs/for-psygym-team.md`：写明病例和督导标准以后在后台改，仓库里的文件是自动导出的副本，提 PR 改不会生效。

**2. 平时（每次发布）**

1. 审核人在后台点「发布」，数据库里生成新的已发布版本。App 从下一次请求起就用它（后端缓存 1 分钟）。
2. 同时记一条「待同步」。同步机器人把这个病例**当前已发布的版本**导出成 `content/` 下的文件，格式和现在完全一样（frontmatter + 正文），提交到 main。
3. **只导出已发布的。** 草稿、待审、退回的内容不导出，只留在后台。
4. 提交信息写病例 id 和版本号，例如 `content: publish cbt-depression-01 v3`。公开仓库，不写人名；谁改的、谁审的记在后台。
5. 导出的文件和仓库里现有的一字不差时，不提交。同一个病例短时间内发布了好几次，只导出最新的一版。

**3. 反方向不同步**

- 仓库里的任何改动都**不会**回到数据库。
- 聆镜的老流程（提 PR 改 `content/`）在切换日停用，有 CI 拦着。
- 万一有人绕过 CI 改了 `content/`（例如管理员直接推），下一次发布这个病例时会被导出覆盖。后台每天比对一次，发现仓库和已发布版本不一致就标出来，由我们处理。

**4. 机器人、权限、失败怎么办**

- **机器人账号：** 用一个 GitHub App（例如「psygym-content-sync」），只装在这个仓库上。权限只给 `contents: write`，不给 issues、PR、设置。密钥存在后端的环境变量里，不进仓库。
- **怎么提交：** 直接提交到 main。main 的分支保护里只给这个 App 例外（绕过 PR 审核）；其他人仍然要走 PR。
- **失败重试：** 导出失败（GitHub 不可用、网络错误、冲突）时，这条「待同步」保留，后端每 10 分钟自动重试，间隔逐次拉长，最多重试一天。一直失败就停下来等人处理。
- **导出失败不影响发布。** 发布在数据库里就生效，App 照常用新版本。后台在病例上显示「未同步到 GitHub」和失败原因，有「重新同步」按钮可以手动重试。
- **谁收到提醒：** 一条记录超过 1 小时还没同步，在我们内部的 Slack 频道发一条提醒（只有病例 id 和版本号）。

## 3. 邀请码管理

把邀请码从环境变量搬进数据库：

| 字段 | 说明 |
|------|------|
| 码 | 随机生成，8–10 位，去掉易混的字符。存哈希；明文只在生成时显示一次。 |
| 名称 | 例「聆镜内测第一批」「10/18 demo 会」 |
| 创建人、创建时间 | |
| 有效期（可选） | 过期自动失效 |
| 作废时间 | 作废后立即生效（后端每次请求查表，加 1 分钟缓存） |

后台能做：新建（可以一次建多个）、改名称、作废。D-A1 选了按码统计的话，还能看每个码每天开始了几场、生成了几份报告。

限流仍按码，但每个码的上限可以在后台调。

## 4. 谁能登录、怎么登录（D-A3 = A，已定：只用 Google）

- **只给 Novawerk 和聆镜的人。** 一张 `admins` 表：邮箱、角色、来自哪边（Novawerk / 聆镜）、是否启用。不在表里的邮箱登不进来。
- **角色：**
  - 管理员：管理人员和邀请码。
  - 审核人：审核、发布病例和督导标准。
  - 编辑：改病例、送审。
  - 只读：看指标。
  - 聆镜的心理学同事默认是「编辑 + 审核人」。
- **登录方式：** 只用 Google 登录，照 Novawerk 现有的做法做。
- 会话：httpOnly cookie，7 天；每次请求重查 `admins` 表，停用立即生效。
- **风险：聆镜的同事在中国大陆，可能打不开 Google 登录。** 这和有没有 Google 账号无关：在大陆的网络里，Google 的登录页本身可能打不开。到时候的办法，按代价从小到大：
  1. 先确认：请聆镜的同事试一次后台登录。能登就不用管。
  2. 他们用自己合规的网络环境（例如在海外时，或单位提供的国际网络）登录；登录后会话 7 天有效，不用天天登。
  3. 加邮件验证码登录。Novawerk 已经有这套做法，照着做，大约一两天的工作量。这是登不上时的正式解法。
  4. Novawerk 帮忙开 Google 账号**解决不了**这个问题（打不开的是登录页，不是没有账号），不建议走这条。

## 5. 隐私

- **存在哪：** 数据库 Neon 法兰克福，后端和后台 Vercel fra1。都在欧盟。
- **存什么：**
  - 按天的匿名计数和时长汇总：不含任何 ID、IP、文字，不算个人数据。
  - 邀请码的哈希和名称。
  - 病例和督导标准的各个版本，以及改的人、审的人：这些是我们自己成员的信息。
  - 后台管理员的邮箱和登录记录：这是我们自己成员的个人数据。
- **保留多久：**
  - 计数和时长汇总：一直留（没有个人数据，留着才能看趋势）。
  - 后台登录日志：90 天。
  - 病例版本：一直留。
  - 反馈和举报：仍只在 Slack，不进数据库。
- **已经改的文档：**
  - `docs/safety.md` §1。
  - 隐私政策 `docs/release/privacy-policy.md`。
  - App 隐私说明 `docs/product/copy.md`、`docs/product/screens.md`（P3）：加一问「我们统计什么？」。
  - 商店隐私标签 `docs/release/privacy-labels.md`：列出要改的地方，由发布成员核对。
- **待办：** 和 Neon、Vercel 签数据处理协议（DPA），和 Novawerk 一样。

## 6. 分期

| 期 | 做什么 | 不做什么 |
|----|--------|----------|
| **demo 前（10/17 前）** | 只开始**匿名计数**和**时长**：建库，建两张表，后端在第 1 节列的几个点加 1；App 在 `/supervision` 里带 `durationSec`（改合同）。有环境变量开关，随时能关。没有后台界面：要看数，用一个受保护的 `GET /admin/stats`（用一个密钥，输出同样套用 <5 和防反推规则），或者直接查库。隐私文档同步改。 | 不做后台界面、登录、邀请码搬家、病例编辑 |
| **Epic 2（圣诞前）** | 后台网页：Google 登录、指标看板（按天、病例、语言的折线和表格，带 <5 阈值）、邀请码管理、病例和督导标准编辑（版本、送审、发布、回滚、导出回仓库）、管理员管理 | 不做用户账号、不做用户级数据 |

**为什么 demo 前就开始计数：** 没采的数据补不回来，demo 前后正是第一批真实使用。

**风险：** 离 demo 一周给后端加数据库，所以计数一律「发出去就不管」，出错不影响请求，并且有开关。数据库挂了，App 照常用。如果 App 来不及在 demo 前带上 `durationSec`，后端的计数照样先上，时长从 App 更新那天开始有。
